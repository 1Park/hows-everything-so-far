# Vision

`server.py:create_app`, default localhost:8001, `POST /v1/analyze`.
Takes a raw JPEG/PNG and returns the type, fill level and bbox for each object. Only the Controller opens the camera.
Select fixture or the external backend below explicitly. There is no automatic fallback.

## DINOv2 backend (`backend.py`)

### Category merging

The existing DINO `.pte` and logistic regression `head.json` are not changed.
After softmax, the probabilities of `coffee` and `coke` are summed and returned as the representative class **`coke`**,
and `water` is kept. Fill levels are not merged, and the existing probability-weighted average is kept.
Drink confidence is computed from the merged probability. So `coke` in observation results also includes coffee.
Coffee requests stated explicitly by the customer, and the menu, can still use coffee as is.
The Controller expands all observed categories in the current frozen scene to build `allowed_items`:
water only gives water, the coke group only gives coke/coffee, and both give all three drinks.
This list is passed to the LLM prompt, and if the model returns a drink outside the list, the Controller
treats it as `not_understood` and blocks confirmation. The customer requests a drink by voice or text.
unknown does not add options. The customer's choice is a request card, not automatic physical approval.

The source of the fixed mapping is `common/vision_categories.py`, and it is applied in `labels.py`.
The read-only display in Demo tools and `GET /api/vision-categories` use the same mapping.
No runtime edit API is provided. This merging applies to DINO backend postprocessing;
the Controller does not force-change results from fixtures or separate external adapters.

Extra sub-drinks are enabled only through the Controller's demo-only toggle (OFF by default).
water → water/sparkling water/soda, coke → coke/coke zero/coffee; no DINO head classes are
added. The observation enum in the Vision contract and the customer request enum are separate.

```sh
VISION_MODEL_BACKEND=external \
VISION_ADAPTER=services.vision.backend:create_backend \
VISION_MODEL_PATH=models/local/vision/<bundle> \
python -m uvicorn services.vision.server:create_app --factory --host 127.0.0.1 --port 8001
```

Settings are read from `common.config.Settings` — write them in the selected env file (`.env`, `.env.board` on the board) or override them with process environment variables.

| Setting | Meaning |
|---|---|
| `VISION_MODEL_PATH` | Bundle directory (`bundle.json`, `.pte`, `head.json`). Relative paths are relative to the repo root. Generated by `ml/export/make_bundle.py` |
| `VISION_RUNNER_BIN` | Path to `qnn_executor_runner` used by the standalone CLI pipeline, training and diagnostics. The resident service uses `VISION_WORKER_BIN` |
| `VISION_WORKER_BIN` | Path to the native worker that keeps DINO and YOLO resident in the service. Required when using a CLI bundle |

- Flow: image bytes → cup boxes (`boxes.mode`: `yolo` .pte / fixed `rois` / `center`) → crop (for `yolo`, default `crop_mode: pad` = box×1.15 + gray padding) → DINOv2 .pte → head → `item`, `fill_ratio`, `confidence`, `item_confidence` ([labels.py](labels.py)).
- If the head has an `other` class (cans, bottles, bags), boxes with p(other) ≥ 0.5, or where `other` is the highest class, are dropped from the results. object_id is renumbered based on the remaining cups.
- In YOLO mode, the head is trained on the same crops as inference (`ml/training/make_crops.py` → `make_head --data data/crops [board-camera crops] --model lda --augment 4`). Board deployment bundle: `models/board/vision/dinov2-qnn-v7` (water, coke, coffee, orange juice × full/mid/low + empty + other, 14 classes; [evaluation](../../docs/vision_evaluation/README.md#board-camera-sessions-at-the-demo-spot-2026-10-18-board-bundle-v7)). Its head is StandardScaler + LDA (shrinkage) trained with ×4 augmentation; it uses the same `head.json` format (`W`, `b`) as the logistic head, so `Head` needs no change. The latency comparison records below used the `dinov2-qnn-v3` bundle at the time.
- At startup, the service loads both DINO and YOLO (detector) and waits for the ready signal. An existing bundle's `runner=cli` is connected to a resident worker inside the service, and the bundle files are not modified. `py` loads the Python runtime model once and keeps it. The `CliRunner` used for training and standalone diagnostics keeps its existing one-shot behavior.
- Dependencies: numpy + Pillow (no OpenCV or ultralytics needed). Inference runs serially on one dedicated thread.
- If the bundle or worker is missing, or loading fails at startup, service startup fails. `/ready` shows whether the actual workers are alive and the resident flag and PID of `runners.dino/detector`. Inference failure, timeout or cancellation reaps that worker and sets ready=false; recover by restarting the service. No automatic switch to fixture/one-shot CLI.
- Does not open the camera (owned by the Controller VideoSource). object_id is unique only within a scene (`cup-0`… from the left).
- Validation: `tests/test_vision_backend.py` (contract and error paths with a fake runner), real HTTP on 6 scenes with a Mac XNNPACK bundle → [evaluation records](../../docs/vision_evaluation/README.md).

## Building and deploying the resident worker

Uses the compiler flags and linked QNN libraries from the organizers' existing SDK/build.
The SDK sources and build directory are not modified; generated sources, objects, binaries and the build manifest are
written only to the specified output path. The stdin extension that already exists in the SDK is also handled only in the generated copy.
Unsupported source/build layouts fail explicitly.

```sh
python scripts/build_vision_worker.py --sdk "$HOME/git/executorch" \
  --build-dir "$HOME/git/executorch/build-x86" --output-dir /tmp/vision-worker-build
```

Experiments copy the local code to `/tmp` and run there. For an official deployment, push the local changes,
place the binary at `models/board/bin/qnn_vision_worker` through the deployment procedure,
set `VISION_WORKER_BIN`, and then restart the Vision service. Even if `.env.board` has the path,
the worker file must be built and deployed separately. An existing process does not switch to
resident mode without a service restart.

Behavior: with `--vision_resident=true`, the worker loads the model, method and QNN context once, and
after `VISION_READY` it handles two lines per request on stdin: the input-list and the output-directory.
Completion is synchronized with `VISION_DONE`. Input and output files are isolated and validated per request,
and ETDump event accumulation is disabled in resident mode. The original QNN inputs/outputs and operations are kept.

## Latency before and after the change

```sh
python scripts/benchmark_vision_residency.py --bundle /actual/bundle \
  --cli /actual/qnn_executor_runner --worker /tmp/vision-worker-build/qnn_vision_worker \
  --image /actual/cups.jpg --output /tmp/vision-latency.json --warmups 3 --repetitions 20
```

With the same image and bundle, runs the CLI 23 times (3 warmup + 20 measured) and then the resident worker 23 times, in order.
It separates pipeline startup load time and the first invoke, the median/mean/p95 of repeated invokes, and boxes/DINO time,
and checks that all outputs are equivalent. This is direct pipeline wall time, excluding HTTP, camera and network.
It is not an OS cold-cache or full-model accuracy check; the raw samples, hashes and PIDs are saved to
new JSON/Markdown files.
